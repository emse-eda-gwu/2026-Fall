What can an interactive chart do that a static one can’t?

The reader can…
  • Hover for exact values
  • Filter to the part they care about
  • Zoom into a crowded region
  • Play through time
  • Scroll through a story, one step at a time
The cost
  • More to build, and more to check
  • Hides information behind a mouse movement
  • Doesn’t work on paper or in a PDF
  • Can be decoration instead of insight

The test: what does the interaction let me do that a static chart wouldn’t?

Two ways to make JavaScript-based graphics

A. Packages that wrap JavaScript

plotly, reactable

  • Hide the JavaScript behind R code
  • Short, readable code you could write yourself
  • Limited to what the package supports
B. Custom graphics with D3

D3 + Claude

  • Build anything you can describe
  • You don’t write it by hand: you prompt and iterate
  • You verify the result against a static chart and the data

Then: Shiny for dashboards, where R runs live behind the page

Turn any ggplot into an interactive chart with ggplotly()

plot <- gapminder %>%
  filter(year == 2007) %>%
  ggplot(aes(x = gdpPercap, y = lifeExp,
             size = pop, color = continent,
             label = country)) +
  geom_point(alpha = 0.7) +
  scale_color_brewer(palette = 'Set2') +
  scale_size_area(
    guide = FALSE, max_size = 25) +
  scale_x_log10() +
  theme_bw(base_size = 16) +
  labs(x = 'GDP per capita',
       y = 'Life expectancy',
       color = 'Continent')

Control what the tooltip shows with the tooltip argument

ggplotly(
  plot,

)

ggplotly() is a translation

Translations lose things

  • Tooltips often show raw aesthetic names (x, y, colour) and unrounded numbers
  • Subtitles, captions, and annotations can move or vanish
  • Fonts and themes don’t always survive
  • Legends can be duplicated or oddly placed

Always compare the interactive version to the static one

Save as html page

htmlwidgets::saveWidget(
  ggplotly(plot),
  file = file.path('figs', 'gapminder.html')
)

Insert using iframe

htmltools::tags$iframe(
  src         = file.path('figs', 'gapminder.html'),
  width       = "100%",
  height      = "400",
  scrolling   = "no",
  seamless    = "seamless",
  frameBorder = "0"
)

B. When packages aren’t enough

What packages can’t do easily

  • A custom scale or axis
  • A custom animation (not just “play through the frames”)
  • A bespoke interaction: linked views, brushing, step-by-step stories
  • A layout nobody wrote a function for
D3
  • The JavaScript library underneath most custom interactive graphics (The Pudding, NYT, The Guardian)
  • It can build anything, so it’s much more complex than ggplotly()
  • Browse the D3 Graph Gallery to see what’s possible

You don’t write D3. You prompt, and iterate.

You
  • Decide what the chart should show
  • Describe it precisely
  • Check that it’s right
Claude
  • Writes the JavaScript
  • Revises until it looks right

How do you verify it without reading the code?

Verify against the data, not the code

  1. Build a static chart first and check it carefully (your ggplot, or a plotly version)
  2. Prompt Claude to bring that same chart to life as an interactive, animated version
  3. Compare the interactive chart to the static one, and to the data

The static chart is your reference. If the two disagree, one of them is wrong, and you can find out which.

The workflow

  1. Make a static chart and verify it
  2. Sketch what the interactive version should do
  3. Prompt Claude with your code, your data, and your sketch
  4. Iterate until it looks right
  5. Verify against the static chart and the data

Example, step 1: a static chart we’ve already verified

What we know from the data:

  • 142 countries in 2007
  • China and India are the biggest bubbles
  • Life expectancy ranges from about 40 to 83 years

Example, steps 2-3: the prompt

Here is my static chart (code below) and the data (gapminder.csv). Build an animated, interactive version in D3:

  • One bubble per country, same axes and colors as the static chart
  • A year slider (1952-2007) and a play button that animates between years
  • Continent filter buttons, and a tooltip on hover
  • A title that states the main takeaway

Put it in a single self-contained file called d3-chart.html, loading D3 from a CDN. Embed the data directly in the file.

Example, step 4: the result

Example, step 5: verify against the static chart and the data

  1. Set the slider to 2007: does it match the static chart?
  2. Hover over a bubble: do the values match the data?
  3. Count the bubbles: 142?
  4. Check the axes: ranges, units, labels
  5. Click everything: first and last year, each filter

Checks for any chart you didn’t write by hand

  1. The numbers. Hover over several points and compare to your data
  2. The axes. Units? Start points? Resize the window: does it still work?
  3. The claim. Does the data support exactly what the title says?
  4. The interaction. Does every control do what it says?

If something looks off, tell Claude exactly what’s wrong and give it the right value from your data

Gotchas

  1. Embed the data in the file. A local .html can’t load a local CSV (browsers block it), and the chart will be blank
  2. Open it in the browser and check the console (right-click → Inspect → Console) for red errors
  3. To embed in a .qmd, the .html must be in the same folder and committed:
<iframe src="d3-chart.html" width="100%" height="500" style="border:none;"></iframe>

library(shiny)

# Define UI for application that draws a histogram
ui <- fluidPage(

    # Application title
    titlePanel("Old Faithful Geyser Data"),

    # Sidebar with a slider input for number of bins
    sidebarLayout(
        sidebarPanel(
            sliderInput("bins",
                        "Number of bins:",
                        min = 1,
                        max = 50,
                        value = 30)
        ),

        # Show a plot of the generated distribution
        mainPanel(
           plotOutput("distPlot")
        )
    )
)

# Define server logic required to draw a histogram
server <- function(input, output) {

    output$distPlot <- renderPlot({
        # generate bins based on input$bins from ui.R
        x    <- faithful[, 2]
        bins <- seq(min(x), max(x), length.out = input$bins + 1)

        # draw the histogram with the specified number of bins
        hist(x, breaks = bins, col = 'darkgray', border = 'white')
    })
}

# Run the application
shinyApp(ui = ui, server = server)

You can deploy an app for free on Posit Connect Cloud

(shinyapps.io is being retired in favor of Connect Cloud)

  1. Sign in at connect.posit.cloud with GitHub
  2. Put your app in a public GitHub repo: app.R + any data files
  3. In R, in the app folder, list the packages the app needs:
rsconnect::writeManifest()
  1. Commit and push manifest.json with the app
  2. On Connect Cloud: Publish → Shiny → your repo → app.R → Publish

Deploy: things that bite

  • No manifest.json, or a stale one → missing package error. Re-run writeManifest(), push, republish
  • Data files must be committed next to app.R, and read with relative paths
  • Don’t call install.packages() inside the app
  • “Automatically publish on push” redeploys every time you push

Bonus: publish your JavaScript graphic on the web

You can take your Quarto file with the D3 (or plotly) graphic and put it on a real URL with GitHub Pages

  1. Create a new public repo (GitHub Desktop)
  2. Add your .qmd and graphic files, plus a _quarto.yml that renders into docs/
  3. Render, then commit and push
  4. On GitHub.com: Settings → Pages → deploy from main / docs
  5. Open https://<username>.github.io/<repo>/

The key setting: render into docs/

# _quarto.yml
project:
  type: website
  output-dir: docs        # default is _site
  resources:
    - d3-chart.html       # copy your D3 file into docs/

The pages-demo folder in your practice files has a starter: index.qmd, _quarto.yml, and a hidden .nojekyll file (in Finder: Cmd+Shift+.)

Three things everyone forgets

  1. Turn Pages on. It’s off by default
  2. Render before you push. Pages serves what’s committed, so a stale or missing docs/ means a stale or missing site
  3. Make the repo public.

And every time you change something: re-render, commit, push
